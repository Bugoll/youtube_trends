### OTUS IT Онлайн - образование — Как работает @Transactional в Spring: границы транзакций и типовые ошибки
- Видео: https://www.youtube.com/watch?v=wv-_bzXQN2I
- Основная тема: Механика работы аннотации @Transactional в Spring Framework, границы транзакций и типовые ошибки разработки

Видео разбирает принципы ACID-транзакций через призму прокси-обёрток Spring AOP. Спикер объясняет, почему самовызов методов внутри одного класса не запускает транзакцию, как правильно определять границы (сервисный слой) и какие проблемы возникают при долгих внешних вызовах.

Основной фокус видео — демистификация работы @Transactional. Транзакции реализуются через прокси-обёртки Spring AOP, которые перехватывают вызовы до передачи метода бизнес-логике. Если метод вызывает сам себя (self-invocation) напрямую из тела класса, транзакция не создаётся, так как внутренний вызов обходит цепочку проксов. Это частая ошибка на собеседованиях и в продакшене.

Ключевое правило: хорошая граница транзакции должна охватывать ровно одну бизнес-операцию (проверка -> изменение состояния -> сохранение) внутри одного сервиса. Контроллеры не подходят для начала транзакций из-за лишнего кода, а репозитории — слишком низкоуровневый слой без знания сценария.

Обсуждаются режимы распространения: 'required' присоединяется к существующей или создаёт новую, тогда как 'required new' приостанавливает внешнюю транзакцию для изолированной внутренней операции (полезно для аудита). Откат по умолчанию происходит только при Runtime исключениях; Checked Exceptions требуют явного @RollbackFor.

Важные нюансы: долгие REST-вызовы внутри открытой транзакции удерживают соединения и persistent context, что ведёт к деградации БД. Логировать успешное изменение данных до коммита нельзя — если откатится транзакция, лог будет ложным.

В конце упоминается курс по промышленному Spring Boot с участием инженеров из компаний Soft и Гринатом.

Ключевые опорные пункты:
- @Transactional работает через прокси-обёртки AOP, перехватывая вызовы до бизнес-логики
- Самовывод (self-invocation) внутри класса не запускает транзакцию из-за обхода цепочки проксов
- Идеальная граница транзакции — одна бизнес-операция в рамках одного сервиса
- Режим 'required new' создаёт изолированную внутреннюю транзакцию, независимую от внешней
- Откат по умолчанию срабатывает только на Runtime исключениях (Checked Exceptions требуют явного указания)
Что можно вытащить как рабочие тезисы из обработанного пакета:
- `fact` / confidence `high`: @Transactional делает всё механически, никакой магии нету.
- `fact` / confidence `high`: При самовызове (self-invocation) внутри одного класса транзакция не будет запущена, так как прокси её перехватить не может.
- `recommendation` / confidence `high`: Вынести операцию в отдельный сервис — лучший и правильный вариант для большинства случаев (99%).
Слабые сигналы / необычные идеи:
- Транзакция — это контракт на границе вызова, а не внутри тела метода
- Разделение трех уровней транзакций: логическая Spring-транзакция, персистентный контекст ORM и физическая транзакция БД.
- Идея о том, что метод repository.save() не всегда означает немедленную запись в базу (особенно при использовании GPA).
